# GigBuddy v1.2.0

Released 2026-08-14. This note covers the work after `v1.1.4`.

## Overview

GigBuddy now treats a downloaded TONE3000 tone and a user-owned local folder as
the same kind of library asset: a Tone Pack containing `.nam` NAM models and
`.wav` IR files. The TONE3000 adapter follows the official search page's
ordering and default filters, and the local library now shows remote and local
Packs together in LOCAL.

GigBuddy exposes and loads only NAM A2 and IR assets. A1, Custom, AIDA-X,
AA-SNAPSHOT, Proteus, and unknown architectures stay out of the catalog and
the download path.

## What's new

### TONE3000 search now follows the official catalog

- An empty search uses the official `trending` order with the default
  `architecture=2` view. A non-empty query defaults to `best-match`.
- The unfiltered result list uses the single ranked stream returned by the
  official search. GigBuddy no longer builds a separate ranking by concatenating
  A2 and IR result lists. IR rows remain visible in the official all-format A2
  view because the architecture filter applies to NAM models; an explicit IR
  filter still narrows the view to IR assets.
- The sort choices match the official search surface: trending, best match,
  most downloaded, newest, and oldest. The separate favorites view shows the
  current user's saved TONE3000 tones. The downloads request uses TONE3000's
  all-time downloads order.
- Search filters are translated to the documented API parameters for gear,
  format, tags, makes, creators, architecture, page, and page size.
- Unsupported rows are removed after each official page is received. GigBuddy
  keeps fetching when a page contains unsupported A1 or Custom rows, so the
  list does not stop short on a page whose rows were all filtered out.
- Repeated page payloads and repeated tone IDs are detected. This prevents an
  inconsistent pagination response from producing duplicate rows or an
  endless load-more loop.

### A2 and IR are the supported product assets

- The same A2/IR rules apply to search, model detail, downloads, the local
  library, Chains, and Presets.
- A mixed TONE3000 Pack remains searchable, but only its supported A2 and IR
  files and counts are offered to the user.
- Raw TONE3000 counters are kept as source metadata. They do not tell you how
  many files GigBuddy can load.
- Downloaded NAM files keep the semantic filename supplied by TONE3000. IR
  files use `.wav`; NAM files use `.nam`.
- Contradictory architecture metadata is rejected; an unsupported model cannot
  slip into a chain.

### Remote Tone Packs

- `gigbuddy tone import <tone-id>` now downloads supported model files and
  persists the complete Tone and Model metadata in the local library.
- Each remote import is stored as one Pack under
  `data/tones/<tone-id>-<title-slug>/`.
- Running the same import again does not create a second Pack. Existing files
  are reused when the recorded size, semantic name, source URL, and SHA-256
  still match.
- TUI Pack installation can be partial: a user can select individual missing
  models, and a later import can complete the same Pack.
- Files are downloaded into a hidden staging directory before being moved into
  the Pack. Failed downloads never appear as installed model files.
- Remote imports create or update a portable `gigbuddy.json` manifest. Existing
  GigBuddy display fields and unknown manifest fields are retained. Invalid or
  foreign JSON is left alone.
- A remote Pack can be installed, inspected, selected into a Slot, used in a
  Chain, saved in a Preset, or uninstalled at Tone or Model level.

### Local Tone Packs

- A user-owned Pack is a directory placed directly under the managed
  `data/tones/` directory.
- GigBuddy scans direct child files with `.nam` and `.wav` suffixes. No
  TONE3000 ID, manifest, or network connection is required.
- `gigbuddy.json` is optional. It can provide a Pack name, author, gear, tags,
  make, description, and per-file display metadata.
- The file extension and its location determine how a local file is treated.
  Manifest metadata can improve display text, but it cannot turn a `.nam` into
  an IR or a `.wav` into a NAM model.
- A missing, invalid, or foreign manifest does not hide valid files. GigBuddy
  falls back to the directory name, filename, and `LOCAL` as the source.
- Local Packs have their own identities. They do not appear in remote search or
  download operations.
- Remote and local Packs appear together in LOCAL and can use the same Chain and
  Preset workflow.

The customer-facing guide is [GigBuddy tone file management](../tone-file-management.md)
([中文](../tone-file-management.zh-CN.md)). It includes the installed and
checkout paths, copy commands, manifest format, refresh behavior, shareable
Presets, and what happens when something goes wrong.

### Shareable Presets

- `gigbuddy preset export NAME [PATH]` writes a portable `preset-name.json`
  whose model references are TONE3000 `model_id` values. It carries the Slot
  order, repeated model references, bypass state, per-Slot trims, chain-level
  gain/master/quality, preset name, and note, but no local path or Pack identity.
- `gigbuddy preset import preset-name.json` resolves missing model IDs through
  TONE3000's exact model lookup endpoint, groups them by parent Tone, and
  downloads only the models used by the shared chain. Models already installed
  locally are reused.
- The local preset is written only after all requested model files are available.
  `--name NAME` changes the local name and `--load` applies the imported chain to
  the live engine. The source JSON is not auto-imported from `data/presets/`.
- A shareable export is valid only for a Preset whose Slots refer to supported
  TONE3000 A2 or IR models. A Preset containing a user-owned local Pack asset
  must be kept as a local GigBuddy Preset instead.

The format and commands are documented in the customer guide's [Shareable
Presets](../tone-file-management.md#shareable-presets) section
([中文](../tone-file-management.zh-CN.md#分享-preset)).

### Chain and Preset support for local assets

- A local model can be selected into any supported Slot alongside a remote
  model.
- Presets store a local Pack identity and relative filename when available, and
  resolve them back to the current file path when loading.
- Chain and Preset validation accepts only managed `.nam` and `.wav` files. A
  file outside `data/tones/`, a missing file, or an unsupported extension is
  rejected.
- The saved live chain contains file paths and chain parameters. It does not
  copy Tone metadata or remote IDs into `data/live_chain.json`.

### Local-library reconciliation

- Local Pack scans can be rebuilt. The Pack folder and optional manifest hold
  the files and metadata; SQLite is only an index.
- File additions, edits, renames, deletions, and manifest edits invalidate the
  local scan cache and refresh LOCAL.
- Missing remote files no longer appear as downloaded. Stale database paths are
  reconciled against the filesystem, while remote metadata is kept for a later
  reinstall.
- Download state is reported as none, partial, or all using only supported A2
  and IR models. It can be unknown when the remote model probe fails.
- Active Chain references and Preset references are checked before uninstall.
  Managed remote files are moved to the application trash directory rather than
  deleted immediately, and remote metadata stays available.
- Normal uninstall checks reject paths outside the managed tone library.
  Replacing the same Pack from another process during an import or uninstall is
  unsupported.

## Fixes and interaction changes

- Fixed newest sorting to use the source timestamps instead of response arrival
  order.
- Fixed most-downloaded sorting to use the official all-time downloads order.
- Fixed mixed Pack classification so a Tone-level IR flag cannot turn an A2
  file into a WAV, and a CAB/SPACE gear value alone cannot misclassify a model
  as IR when explicit metadata says otherwise.
- Fixed stale local rows, active markers, Pack/model detail, and downloaded
  counts after files are removed or replaced on disk.
- Fixed late remote refreshes from moving focus, selection, or the active Slot
  away from the user's current view.
- Fixed load-more behavior for short pages, duplicate pages, filtered pages,
  and views that exactly fill the table viewport.
- Added staged imports, atomic manifest writes, semantic filename preservation,
  and model-level reuse checks.
- Added model-level uninstall handling that keeps the remaining files and Tone
  metadata when only part of a Pack is removed.

## Compatibility and limits

- macOS is still the supported native-audio platform. `--no-engine` can still be
  used to browse and manage the library without live audio.
- Existing remote Tone metadata, old relative/absolute local paths, legacy
  flat `model`/`ir` Presets, and existing Slot Presets stay readable as long as
  their files are present and supported.
- A local Pack must be inside the managed `data/tones/` root. The scanner only
  looks one directory level deep; nested `.nam` or `.wav` files are ignored.
- Moving a local Pack does not migrate existing Presets automatically. Open
  LOCAL, select the moved files again, and save the affected Presets.
- GigBuddy checks paths, extensions, and file existence. It does not validate
  the internal contents of a NAM or WAV file before the native engine loads it.
- There is no `tone import-local` command in this release. To add a local Pack,
  copy its directory into the managed `data/tones/` directory and refresh
  LOCAL.
- TONE3000 search, model details, and remote downloads require network access
  and the user's own TONE3000 session. Imported files and local Packs are
  available offline.
- The official TONE3000 API documentation and terms still govern OAuth scope,
  rate limits, attribution, and commercial use.
- Do not let another process rename, replace, or delete the same managed Pack
  while an import or uninstall is running. Changes made by another process at
  the same time are unsupported.
